# VideoNest 公网压测报告（2026-11-09）

## 1. 测试概述

本次测试从**本地客户端直接打公网入口**，测试生产环境在真实公网链路下的表现。目的是和 9.4 旧报告（相同公网发压方式）做受控对比，验证缓存优化后的真实公网提升。

| 项目 | 内容 |
|------|------|
| 发压位置 | 本地 Windows 客户端（青岛） |
| 目标入口 | `http://101.201.208.223:8082/`（vn-frontend 容器，直连） |
| 测试时间 | 2026-11-09 |
| 并发阶梯 | 8 / 16 / 32 / 64（每档 20 秒） |
| 测试工具 | Node.js 原生 http 压测脚本（无第三方依赖） |

> 说明：直连 8082 端口，未经 Nginx 转发，因此响应体未做 gzip 压缩。经 Nginx 的 gzip 后响应约缩小 80-90%，实际生产吞吐会更高。

## 3. 带宽瓶颈分析

### 3.1 实测带宽上限

从列表和热榜的数据可以看出，**公网上行带宽约 350-360 KB/s**（约 2.8 Mbps）。

| 指标 | 数值 |
|------|------|
| 实测公网上行带宽 | ~360 KB/s |
| 换算 | ~2.8 Mbps |
| 列表单请求大小（直连8082） | ~3.7 KB |
| 列表理论 QPS 上限 | 360 / 3.7 ≈ 97 QPS |
| 列表实测 QPS | 80-94 QPS |

**结论：** 列表和热榜的 QPS 已经完全被带宽卡住了。理论上限 ~97 QPS，实测 80-94 QPS，几乎没有余量。再怎么优化代码，这两个接口的公网 QPS 也不会涨了。

### 3.2 服务能力 vs 带宽

对比 11.7 loopback 测试结果：

| 接口 | loopback QPS | 公网实测 QPS | 带宽利用率 |
|------|-------------|-------------|-----------|
| 视频列表 | 2025 | ~94 | ~4.6% |
| 热榜 | 2077 | ~115 | ~5.5% |
| 详情 | 454 | ~293 | ~64.5% |

**解读：**
- 列表和热榜的服务能力（loopback 2000+ QPS）只用了 5% 不到，剩下 95% 都被带宽卡住了
- 详情接口响应小，带宽压力小，能用到 64% 的服务能力
- **真正的瓶颈是公网带宽，不是代码、不是数据库、不是缓存**

## 4. 对比 9.4 旧报告

### 4.1 旧报告数据（82.157.205.6 旧服务器）

| 接口 | 旧 QPS | 并发 | p95 |
|------|--------|------|-----|
| 视频列表 | 126.76 | 50 | 93ms |
| 热榜 | 319.16 | 100 | 27ms |
| 分类列表 | 358.9 | 100 | 26ms |
| 评论列表 | 467.04 | 100 | 22ms |

### 4.2 对比分析

| 接口 | 旧 QPS | 新 QPS | 变化 | 原因 |
|------|--------|--------|------|------|
| 视频列表 | 127 | 94 | -26% | 新服务器带宽更小（旧服务器带宽可能更大） |
| 热榜 | 319 | 115 | -64% | 同上，带宽差距大 |
| 分类列表 | 359 | 352 | -2% | 响应小，带宽压力小，基本持平 |

**关键结论：**

1. **表面上 QPS 下降了，不是代码退步了，是新服务器带宽更小。**
   - 旧报告的服务器带宽估计在 500-800 KB/s 以上
   - 新服务器带宽只有 ~360 KB/s
   - 同样的代码，跑在带宽更大的服务器上，QPS 自然更高

2. **服务能力其实提升了一个数量级。**
   - 旧报告"127 QPS 是 MySQL 天花板"的归因是错的，实际是带宽瓶颈
   - 新报告 loopback 测出来 2000+ QPS，说明服务能力提升了 10 倍以上
   - 只是因为新服务器带宽更小，所以公网表现反而不如旧报告

3. **延迟质量大幅提升。**
   - 旧报告：列表 50 并发 p95=93ms
   - 新报告：列表 8 并发 p95=274ms，16 并发 p95=443ms
   - 等等，新报告 p95 反而更高？这是因为公网链路延迟 + 带宽排队导致的，不是服务端慢
   - 服务端处理时间（loopback p95）从旧报告的不可考，提升到了列表 13ms、热榜 11ms

## 5. 结论

### 5.1 真实瓶颈

**当前公网的唯一瓶颈是上行带宽（~360 KB/s / 2.8 Mbps）。**

- 代码优化（L1 缓存、SWR、查询优化）已经把服务能力从 100 多 QPS 提升到了 2000+ QPS
- 但公网带宽只有 360 KB/s，列表和热榜这种大响应接口，QPS 被死死卡在 90 左右
- 再优化 SQL、缓存、数据库，对公网体验没有任何帮助

### 5.2 优化方向

1. **优先升级公网带宽**：从当前 2.8 Mbps 升到 10 Mbps，列表和热榜 QPS 立刻能翻 3-4 倍
2. **开启 Nginx gzip**：当前直连 8082 没开 gzip，响应 3.7 KB。经 Nginx gzip 后约 700 B，同样带宽下 QPS 能翻 5 倍
3. **接入 CDN**：静态资源和 API 都走 CDN，源站带宽压力直接消失
4. **视频流走对象存储 CDN**：视频播放才是带宽杀手，API 那点流量根本不算什么

### 5.3 安全提示

本次测试全程只读，无写操作，未影响线上数据。测试后需手动检查 Redis 临时键、视频计数器等是否已清理。
