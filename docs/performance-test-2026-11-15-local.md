# VideoNest 本地读写压测报告（2026-11-15）

## 1. 测试概述

本次是在本机 Windows + Docker Desktop 环境下的 loopback 读写压测，目标是拿到同一台机器上 VideoNest（Java 21 / Spring Boot 4.1）单实例的真实并发上限，并与同日学习平台（Go 1.27 / go-zero）压测做同口径对照。

| 项目 | 内容 |
|------|------|
| 测试时间 | 2026-11-15 |
| 宿主机 | Intel i7-13700H，14 核 20 线程，15.6 GB 内存 |
| Docker 资源 | 7.57 GB 内存，无 CPU 配额限制 |
| 目标入口 | `http://127.0.0.1:8080`（videonest-backend 直连，不经 Nginx） |
| 应用栈 | Spring Boot 4.1 + Tomcat（max-threads 200 / accept-count 300 / max-connections 2000）、Hikari 连接池 16、Redis 连接池 16、MySQL 8.4、RabbitMQ、MinIO |
| 发压工具 | `docs/performance-results/2026-11-15-local/harness/bench.js`（Node 22 原生 http，无第三方依赖，keep-alive 闭式并发） |
| 并发阶梯 | 读 8 / 16 / 32 / 64，写 4 / 8 / 16，混合 16 / 32，每档 20 秒 |
| 预热 | 每轮 8 秒预热（8 并发，不采集） |
| 隔离条件 | 测试期间学习平台整套容器已停止，宿主机只跑 VideoNest 栈 + 发压进程 |

## 2. 数据夹具

- 视频 34 条，其中 PUBLISHED 且在库作者齐备的 12 条用于详情/评论读，避免历史种子数据外键缺失导致的 404。
- 4 个探针账号 `vnbench_1..4`，通过 `/api/auth/register` + `/api/auth/login` 取得 JWT，用于点赞与评论。
- 评论接口有业务限流：同一用户 60 秒内最多 5 条，这是产品保护策略，不是服务能力上限，单列说明。

## 3. 读场景结果（混合 5 类读接口）

权重：热门榜 25%、列表 25%、详情 20%、评论列表 15%、分类 15%。

| 并发 | QPS | P50 | P95 | P99 | 成功率 |
|------|-----|-----|-----|-----|--------|
| 8 | 2658.27 | 2.60 ms | 5.66 ms | 8.24 ms | 100% |
| 16 | 2951.67 | 4.75 ms | 9.97 ms | 14.34 ms | 100% |
| 32 | 3145.59 | 9.25 ms | 16.57 ms | 20.76 ms | 100% |
| 64 | 2920.77 | 18.40 ms | 43.63 ms | 55.61 ms | 100% |

分接口（32 并发，QPS 为该场景分摊值）：

| 接口 | QPS | P95 |
|------|-----|-----|
| 热门榜 `/api/videos/hot?limit=10` | 782.41 | 16.02 ms |
| 列表 `/api/videos?page=1&size=12` | 795.81 | 16.32 ms |
| 详情 `/api/videos/{id}` | 629.05 | 16.73 ms |
| 评论列表 `/api/videos/{id}/comments` | 468.14 | 17.48 ms |
| 分类 `/api/categories` | 470.19 | 16.71 ms |

结论：读路径在 32 并发达到峰值 3145 QPS，64 并发时 QPS 回落 7%、P95 从 16.6 ms 涨到 43.6 ms，拐点明确出现在 32—64 之间。8 并发时 2658 QPS 已相当高，说明 Caffeine 本地缓存 + Redis 二级缓存把大部分读请求挡在 DB 之前；继续加并发不再带来吞吐，只增加排队。

## 4. 写场景结果

### 4.1 点赞切换（POST/DELETE 严格交替，走 Redis 计数 + MySQL 点赞表与计数更新）

| 并发 | QPS | P50 | P95 | P99 | 成功率 |
|------|-----|-----|-----|-----|--------|
| 4 | 1103.54 | 3.29 ms | 6.03 ms | 9.88 ms | 100% |
| 8 | 1625.34 | 4.70 ms | 7.35 ms | 9.37 ms | 100% |
| 16 | 2036.68 | 7.54 ms | 11.37 ms | 14.48 ms | 100% |

### 4.2 发布评论（每用户 5 条/分钟限流）

| 并发 | 请求 QPS | 成功 | 失败 | 状态码 | P95 |
|------|----------|------|------|--------|-----|
| 4 | 1153.23 | 0 | 23066 | 429 × 23066 | 5.86 ms |
| 8 | 1862.01 | 0 | 37246 | 429 × 37246 | 5.93 ms |
| 16 | 2172.54 | 20 | 43438 | 200 × 20 / 429 × 43438 | 9.61 ms |

结论：评论写入的真实业务上限是 5 条/分钟/用户，4 个探针账号理论峰值约 0.33 QPS，压测请求绝大部分在限流器就被 429 拒绝，延迟只有 3—9 ms，说明拒绝路径本身很轻。这一组数据不能解读为“服务只能写 0.33 QPS”，它衡量的是限流阈值，不是数据库写入能力；数据库写入能力请看点赞场景。

## 5. 读写混合场景（读 5 类 + 点赞写，约 20% 写）

| 并发 | QPS | P50 | P95 | P99 | 成功率 |
|------|-----|-----|-----|-----|--------|
| 16 | 3187.03 | 4.51 ms | 8.22 ms | 10.83 ms | 100% |
| 32 | 3072.52 | 9.85 ms | 13.96 ms | 19.54 ms | 100% |

混合场景 16 并发就达到 3187 QPS，比纯读峰值还高，原因是点赞写路径本身比读接口更轻，摊薄了整体平均耗时。32 并发时写占比相同但总吞吐略降，说明写请求开始与读请求争抢 Hikari 连接池（16 个连接）。

## 6. 瓶颈判断

- 读路径瓶颈不在数据库。8 并发即 2658 QPS，命中本地缓存后单请求 P50 仅 2.6 ms；32 并发以上吞吐不再增长，是 Tomcat 工作线程（200）与 CPU 上下文切换共同作用的结果。
- 写路径瓶颈在连接池与单行更新争用。点赞 16 并发 2037 QPS、P95 11.4 ms，尚未出现错误，但 P99 已从 9.9 ms 抬到 14.5 ms，说明 Hikari 16 个连接接近饱和。
- 评论限流把写入量压到业务可接受范围，限流器本身没有成为性能负担（429 响应 3—9 ms）。
- 未采集容器级 CPU 采样，本报告不声称 CPU 已打满；从吞吐平台期判断更可能是线程/连接池而非 CPU 单点。

## 7. 优化建议

1. 若目标是更高读吞吐，优先调大 Tomcat `max-threads` 到 400 并同步扩大 Hikari 到 32，再复测拐点，否则单纯加并发只会抬 P99。
2. 点赞路径可考虑把计数更新合并成批量回写（类似播放量），把每个赞一次 UPDATE 改为按秒聚合，能明显降低连接池占用。
3. 评论限流阈值 5 条/分钟偏紧，可按用户等级分档，并在 429 响应里带 `Retry-After`，前端体验更可控。

## 8. 复现方式

```bash
node docs/performance-results/2026-11-15-local/harness/bootstrap.js \
  docs/performance-results/2026-11-15-local/harness/tokens.json vnbench \
  http://127.0.0.1:8080 /api/auth/register /api/auth/login

node docs/performance-results/2026-11-15-local/harness/bench.js \
  --config=docs/performance-results/2026-11-15-local/harness/scenarios.json \
  --out=docs/performance-results/2026-11-15-local/raw \
  --label=read --suite=read --secs=20 --ladder=8,16,32,64
```

写场景把 `--suite` 换成 `write --scenario=like-toggle`（或 `comment-create`），阶梯改 `4,8,16`。
